# ESP32 AutoMesh

Экспериментальная сеть **Bluetooth Mesh на ESP32** с Wi-Fi-панелью шлюза и ручным подтверждением новых устройств по OOB.

## Состав проекта

- `gateway/` — BLE Mesh Provisioner, веб-панель, обнаружение узлов, Wi-Fi, адресные команды.
- `node/` — ESP32 Mesh Node/Relay, поддержка индикации и команды «Найти».
- `Windows-Installer/` — исходники установщика первоначальной USB-прошивки для Windows.
- `docs/` — инструкция по восстановлению сети и известные ограничения.
- `.github/workflows/` — проверка сборки ESP32-C3 вне пользовательского ноутбука.

## Изменения v0.3.2-dev (исходный код)

- Включено **постоянное хранение состояния Bluetooth Mesh** на шлюзе и узлах (`CONFIG_BLE_MESH_SETTINGS=y`).
- Шлюз восстанавливает список из таблицы ESP-IDF, а сохранённые названия — из NVS, без удаления недоступных устройств.
- Появилось изменение **имени устройства** (до 48 байт UTF-8) в веб-панели, имя сохраняется после перезагрузки.
- Команда **«Найти»** теперь включает инициализацию vendor-клиента, привязку к AppKey и ожидание подтверждения узла. При отсутствии ответа панель сообщает об ошибке, а не о доставке.
- Автоматическое стирание NVS при ошибке хранения отключено для защиты ключей и настроек.

**Статус:** изменения в исходниках; функциональность нужно подтвердить компиляцией и тестированием на платах. Сам факт публикации кода не обновляет прошивки устройств.

## Совместимость

Ранее проверенные физические платы: ESP32-C3 SuperMini, 4 МБ Flash. LED GPIO8 active-low. Для ESP32-S3 существуют отдельные рабочие материалы/сборки; GPIO встроенного светодиода зависит от платы. Другие семейства и ёмкости Flash нельзя прошивать бинарным образом от C3.

**Внимание при обновлении с v0.3.0-dev:** старые прошивки имели выключенное хранение Mesh-ключей. После установки новой версии на шлюз и на узлы может потребоваться **однократно повторить регистрацию через OOB**. Не стирайте NVS без проверенной резервной копии. См. [восстановление Mesh](docs/MESH-RECOVERY.md).

## Ограничения и безопасность

- Адресное OTA по Bluetooth Mesh пока не реализовано.
- Команда «Найти» работает только с зарегистрированными узлами, у которых привязана vendor-модель. Сквозное испытание после этих исправлений ещё требуется.
- Публичный HTTP не предназначен для Интернета; нужен VPN/HTTPS и дополнительная защита.
- Не публикуйте Flash-дампы, Wi-Fi-пароли, Mesh-ключи, OOB-коды, токены панели и журналы с секретами.
- Локальные резервные копии на пользовательском ПК хранятся отдельно от репозитория.
- Используем только основную ветку `main`, без дополнительных веток.

Основа ESP-IDF 5.5.3; примеры Espressif сохраняют свои лицензионные уведомления. Публикация коммерческой прошивки потребует проверки идентификатора производителя BLE Mesh и лицензий.


## Первый запуск с открытой точкой доступа (v0.3.3-dev)

Если сохранённой Wi-Fi сети нет, шлюз запускает точку доступа `AutoMesh-XXXXXX` **без пароля**. Откройте `http://192.168.4.1/`, создайте ключ администратора длиной от 6 символов и после этого настройте Wi-Fi роутер через сканирование сетей. В памяти ESP32 хранится соль и PBKDF2-хеш ключа, не его открытое значение. Ключ можно изменить в панели; прежний 32-символьный токен для уже настроенных шлюзов продолжит работать до замены.

**Предупреждение:** открытая точка доступа уязвима к захвату первоначальной настройки или перехвату данных поблизости. Настраивайте шлюз в контролируемом месте и сразу подключайте его к защищённому роутеру. Подробнее: [Первый запуск](docs/FIRST-BOOT-ADMIN.md).

## Исправлена блокировка HTTP 429 (v0.3.4-dev)

В предыдущей версии при неверном или устаревшем ключе браузер отправлял
несколько авторизационных запросов каждые 3 секунды и самостоятельно
вызывал временную блокировку HTTP 429. Теперь после первого ответа 401
панель прекращает опрос, удаляет неверный ключ из sessionStorage и
предлагает войти заново. HTTP 429 показывает время ожидания из заголовка
Retry-After и также останавливает опрос. Запросы статуса выполняются
последовательно, без параллельных неудачных проверок.

Ограничение попыток ввода на шлюзе сохранено: это защита от перебора
административных ключей. При старой прошивке v0.3.3-dev временно
нажмите «Отключиться», дождитесь 30 секунд и войдите с верным ключом.
Обновление приложения выполняется без стирания NVS и ключей Mesh.


## Регистрация без отдельного OOB (v0.3.5-dev)

Регистрация нового узла разрешается администратором через веб-панель и больше не запрашивает отдельный OOB-код. Узел использует Bluetooth Mesh No OOB. Подробности и ограничения безопасности: [Регистрация без OOB](docs/NO-OOB-REGISTRATION.md).


## Обновление шлюза из веб-панели (v0.3.6-dev)

После входа в шлюз откройте **Обновление прошивки шлюза**, выберите
gw-c3.bin или gw-s3.bin
из Windows-архива под вашу модель и нажмите кнопку обновления. Новая
прошивка записывается в неактивный OTA-раздел, ESP-IDF проверяет
совместимость чипа, контрольную сумму образа и имя проекта. После
проверки шлюз перезагрузится. Wi-Fi, имена и ключи Mesh в NVS
**не стираются**. Используется загрузчик с откатом.

Ручная установка по USB: установщик теперь **всегда требует выбрать
контроллер**, даже когда подключена одна плата, затем отдельно выбрать
роль «Шлюз» или «Узел». Для окончательной записи подтверждается выбранный
COM-порт; MAC перепроверяется после резервного копирования.

Ограничения: веб-обновление распространяется только на **шлюз**, не на
удалённые BLE Mesh узлы. Для OTA требуется уже установленная прошивка
со встроенным веб-обновлением; для первого перехода обновите шлюз через
USB. HTTP без TLS не защищает административный ключ от наблюдателя в
той же сети — используйте защищённую локальную сеть/VPN, не публикуйте
порт в интернете. OTA-разделы уже должны соответствовать штатной
разметке проекта.

## Изменения v0.3.12-dev: отображение устройств

- В веб-панели скрыт UUID. Технический идентификатор сохраняется только
  внутри запросов и в API, чтобы не перепутать устройства.
- Для зарегистрированных узлов доступна кнопка **«Удалить устройство»**.
  Запрос подтверждается администратором, а шлюз удаляет запись из
  ESP-BLE-MESH Provisioner, своего реестра и резервного NVS-кеша.
  Если SDK отклонит удаление, запись не скрывается навсегда.
- Удаление **не выполняет сброс физического узла**, не стирает его Mesh
  NetKey/AppKey и не делает глобальную ротацию Mesh-ключей. Для
  повторной регистрации сбросьте Mesh на самом узле. Для отзыва
  сетевого доступа скомпрометированного узла нужна ротация NetKey.
- Доработка реализована только на шлюзе; приложение узла использует
  тот же протокол, версии прошивок синхронизированы для выпуска.
- Сборка всех четырёх прошивок и ZIP выполняется через GitHub Actions.
  Реальные удаления необходимо проверять на тестовом узле.

## Единое обновление через веб — v0.3.13-dev

В веб-панели вместо двух отдельных OTA-форм появился один раздел
**«Обновление прошивки»**: выбрать шлюз или один зарегистрированный
OTA1-узел, выбрать целый ZIP GitHub Release либо подходящий APP `.bin`,
нажать **«Обновить»**. Панель определяет чип ESP32-C3/ESP32-S3, роль
`provisioner/onoff_server` и версию из ESP-IDF образа, а SHA-256
вычисляет автоматически. При несовместимости отправка блокируется.
Шлюз передаёт прошивку по Wi-Fi, узлам — по BLE Mesh с прогрессом и
возможностью остановить передачу. При исчезновении узла выбор
**не переключается незаметно на шлюз**. Обновления только вручную,
NVS и Mesh-ключи сохраняются. ZIP распаковывается браузером без
сторонних сервисов (если поддерживается deflate-raw), иначе .bin.
Веб-OTA узлов остаётся экспериментальной до испытаний на оборудовании.

## v0.3.15-dev — надёжность OTA узлов и расположение Wi-Fi

Исправлен потенциальный источник `ESP_ERR_TIMEOUT` в BLE Mesh OTA.
Раньше узел вызывал `esp_ota_begin(part, size,...)` в callback
Bluetooth Mesh, что могло надолго блокировать обработку пакетов при
предварительном стирании всего Flash-образа. Теперь START/DATA/FINISH/ABORT
копируются в очередь и исполняются отдельной FreeRTOS-задачей; с
`OTA_WITH_SEQUENTIAL_WRITES` Flash стирается по мере записи.
Шлюз повторяет START и DATA при пропаже ACK до 3 раз, логирует
номер узла, этап, смещение, число попыток; периодические Mesh-ping
приостанавливаются, пока идёт OTA. Повторный START с тем же сеансом
узел подтверждает, не уничтожая принятую сессию. Веб-панель показывает
этап сбоя; пользовательское имя `ESP_ERR_TIMEOUT` не скрывается.

**Для узла со старым OTA1, который не подтверждает START, может
потребоваться первоначальная USB-прошивка исправленной версии.**
USB-установщик не очищает NVS по умолчанию. Испытания на реальных
C3/S3, при потере пакетов и при обрыве питания ещё обязательны.

Раздел **«Настройки Wi-Fi шлюза»** перенесён почти в самый низ
веб-панели, сразу перед «Сменить ключ администратора». Оба раздела
сохраняют прежние функции и API.


## Интерактивная карта BLE Mesh — v0.3.16-dev

В панели шлюза появилась вкладка **«Карта Mesh»** рядом со списком
устройств. Шлюз и зарегистрированные узлы представлены перетаскиваемыми
элементами; есть изменение масштаба, панорамирование, кнопки
«Обновить данные» и «Сбросить вид». Цвет линии — примерный RSSI
(`dBm`), сплошная линия означает наблюдение в обоих направлениях,
пунктирная — в одном. Узел без свежих наблюдений показывается без линий.

Для **реальных соседей**, а не вымышленных фиксированных маршрутов,
новые прошивки узлов посылают краткий AppKey-защищённый BLE Mesh
маяк `AUTOMESH_NEIGHBOR_BEACON` с **TTL=1**. Такой пакет не
ретранслируется. Принимающий узел измеряет `ctx.recv_rssi` и раз
в ~60–72 секунд отправляет шлюзу компактный отчёт (три самых сильных
соседа). Шлюз также измеряет соседей, чьи маяки принимает напрямую.
В `GET /api/mesh/topology` после авторизации возвращаются только
свежие подтверждённые наблюдения для зарегистрированных ESP32.
Измерения старше 210 секунд скрываются. Ни история сигналов, ни
расположение узлов в NVS не записываются.

**Важно:** BLE Mesh работает как сеть ретрансляторов, а не набор
постоянных родительских соединений. Карта показывает физическое
радиососедство, а не гарантированный маршрут каждого пакета.
Для показаний RSSI и рёбер прошивки узлов должны поддерживать
`v0.3.16-dev`; старые узлы будут видны, но без достоверной
информации о соседях. Узлы со старой прошивкой OTA1, испытывающие
`ESP_ERR_TIMEOUT`, могут потребовать USB-обновления без очистки NVS.
Всё проверять сначала на одной группе тестовых узлов.


## v0.3.17-dev — исправление Mesh OTA (потеря ACK)

Исправлена причина постоянного `ESP_ERR_TIMEOUT` при попытке обновить
узел через шлюз. `gateway/main/main.c` раньше обрабатывал ответный
вендорный `AUTOMESH_NODE_OTA_STATUS` только через
`ESP_BLE_MESH_MODEL_OPERATION_EVT`. Однако клиентская модель ESP-IDF
для `esp_ble_mesh_client_model_send_msg(... need_rsp=false)`
передаёт непарный STATUS через
`ESP_BLE_MESH_CLIENT_MODEL_RECV_PUBLISH_MSG_EVT`. Добавлена обработка
обоих вариантов с сохранением проверки узла, ID сессии и offset.
Узел теперь отправляет `AUTOMESH_NODE_OTA_STATUS` с явным
`reply.send_ttl = 5`, чтобы ответ мог пройти по Mesh через Relay.
Журналирование ответов ограничено, чтобы не перегружать OTA.

**Сначала обновите шлюз по Wi-Fi, потом один тестовый узел по Mesh.**
Для старых узлов, чей ответ не проходит через ретрансляторы, может
понадобиться USB-обновление с сохранением NVS. GitHub Actions
проверяет сборку, но не заменяет тесты на реальных устройствах.

Интерфейс шлюза разделён на три вкладки:

не изменены. Карта остаётся экспериментальной до проверки RSSI
на реальных устройствах.


## v0.3.19-dev — адаптивное ускорение Mesh OTA и оценка времени

Обнаружено, что старый веб-протокол передавал по одному
`96`-байтному блоку с отдельным HTTP-запросом и отдельным
подтверждением BLE Mesh на каждый блок. При измеренной пользователем
скорости **1% за 10 минут** полная прошивка может занять около 16 ч 40 мин.

- Узлы **OTA2** в версии v0.3.19-dev поддерживают блок `224` байта
  вместо `96`, при том же AES-шифровании Mesh, контроле offset,
  AppKey и проверке SHA-256. Это уменьшает число подтверждений
  приложения/HTTP-запросов примерно в 2,3 раза, **но не гарантирует
  пропорционального ускорения времени**, потому что крупные сообщения
  сегментируются нижним транспортом BLE Mesh.
- Узлы старых версий **OTA1** продолжат получать максимум 96 байт.
  Шлюз определяет режим только по явно полученной от узла строке
  версии `OTA1`/`OTA2`, сообщает `max_chunk` веб-клиенту и
  повторно проверяет длину каждого DATA на сервере. Никакого
  предположения о поддержке быстрых пакетов нет.
- В веб-панели видны точный процент, фактическая средняя скорость
  (байт/с), ориентировочное оставшееся время и OTA1/OTA2.
- Сервер сохраняет поэтапные подтверждения, повторные попытки,
  право прервать обновление, проверку прошивки и SHA-256 до смены
  загрузочного раздела. NVS и Mesh-ключи не стираются.
- **Первое обновление старого OTA1-узла останется медленным**:
  новый формат требует обновления прошивки самого узла.
  Для ускорения первого перехода используйте USB-установщик без
  очистки NVS. При Wi-Fi-обновлении шлюза обновляйте только
  `gw-c3.bin` или `gw-s3.bin`; узлы — `node-c3.bin`/`node-s3.bin`.
- BLE Mesh имеет низкую пропускную способность. Для действительно
  быстрых мегабайтных обновлений потребуется отдельный транспорт
  (например, защищённый Wi-Fi OTA) либо Bluetooth Mesh BLOB/DFU,
  а не только изменение размера пакета. Нужны реальные тесты OTA2,
  особенно через Relay и при слабом радиосигнале.


## v0.3.20-dev — меню устройств на карте и диагностика прямых соседей

Во вкладке «Карта Mesh» короткое нажатие на зарегистрированное устройство
открывает **контекстное меню** поверх карты. Там показываются название,
адрес, состояние, версия прошивки, измеренные прямые радиососеди,
RSSI и качество сигнала (хорошее/среднее/слабое). Кнопка
**«Найти устройство»** использует существующий `POST /api/locate`
и `GET /api/locate/status`; результат отображается в том же меню.
Шлюз не выполняет команду поиска самого себя. Меню расширяемое:
будущие команды добавляются в `meshMenuActions`. Поддерживается
закрытие крестиком, Escape и переключением вкладок. Перетаскивание
и масштабирование карты сохранены. Постоянные блоки во вкладку не
добавлены — только контекстное меню по нажатию.

**Исправление пустых линий карты.** При приёме TTL=1-маяка
`recv_rssi` может быть неизвестным (`0` или `-128`). Прежде
наблюдение отбрасывалось полностью, и связь пропадала с карты.
Теперь действительная непосредственная связь показывается серой
линией с пометкой «RSSI не измерен»; неизвестный уровень нельзя
превращать в выдуманное значение. Узлы тоже больше не отбрасывают
такие маяки, а передают шлюзу `-128` как признак неизвестной
мощности. В `GET /api/mesh/topology` RSSI в этом случае `null`,
добавлены счётчики принятых маяков/отчётов и возраст последнего
сообщения (`diagnostics`). Данные только в RAM, без истории и NVS.

**Важно:** Bluetooth Mesh не держит постоянный parent-node.
Линии показывают прямое радиососедство по маякам с TTL=1;
они не раскрывают точную последовательность ретрансляторов,
использованную каждым сообщением. Для появления линий на
независимых узлах должны стоять прошивки с поддержкой карты
(`>=v0.3.16-dev`); на старых узлах могут быть доступность
и версия, но не сведения о соседях. На плотной или слабой сети
измерения могут появляться спустя несколько минут.
Испытания настоящих C3/S3 и проверка соседей обязательны.


## v0.3.22-dev — краткое отображение версии узла

В таблице **«Устройства»** и контекстном меню карты отображается
только версия прошивки и тип ESP32. Например, внутренний ответ узла
`0.3.22-dev C3 OTA2 f5084177` показывается как `0.3.22-dev C3`.
Отсекаются только служебный маркер OTA1/OTA2 и идентификатор
сборки **на уровне пользовательского интерфейса**. Оригинальная
строка `firmware_version` остаётся неизменной в API и хранится
в данных шлюза. Выбор протокола OTA1/OTA2, типа файла C3/S3 и
размера блока продолжает использовать полную строку.


## v0.3.22-dev — пакетная HTTP-передача OTA

Браузер передаёт до четырёх блоков через один HTTP-запрос `/api/ota/node/batch` вместо отдельного запроса на каждый блок. Шлюз последовательно отправляет каждый блок по BLE Mesh и ожидает подтверждение узла; совместимость OTA1/OTA2, SHA-256 и откат сохраняются. При ошибке пакет не повторяется вслепую: текущая сессия прерывается, чтобы не допустить рассинхронизации. Это снижает HTTP-накладные расходы, но не гарантирует ускорение самого BLE Mesh; нужна проверка на реальных устройствах.


## v0.3.23-dev — experimental OTA3 over existing BLE Mesh

- New OTA3 firmware **explicitly advertises** `OTA3` in the firmware-version response. The gateway selects OTA3 only for an approved online node that advertises it; OTA1/OTA2 remain unchanged.
- Sender submits one 224-byte segmented access message at a time, waits for the ESP-BLE-MESH **send-complete** callback to avoid simultaneous segmented sends, then requests a **CHECKPOINT** after up to four packets (896 bytes). The receiver reports the first uncommitted byte. Lost data is retried from that offset, not blindly from the beginning.
- The receiver writes to an inactive OTA partition using its existing FreeRTOS Flash worker and validates SHA-256, ESP image header, project, and rollback before activating. NVS and Mesh keys are not erased. The browser still streams batches; it must remain open.
- This is an **AutoMesh vendor protocol**, inspired by the block-level acknowledgements in Bluetooth Mesh BLOB Transfer. It is **not Bluetooth SIG BLOB Transfer/DFU**. Full BLOB interoperability and ESP-NOW OTA are **not implemented**. They require security and multi-hop radio testing.
- Flash on 4 MB boards has two 1.75 MiB app slots plus a 384 KiB storage partition. Staging a whole app on the gateway would overwrite a rollback slot or require repartitioning; background OTA independent of browser is therefore not enabled.
- **Upgrade order**: first gateway via Wi-Fi or USB, then one test node via its existing OTA2 or USB; OTA3 is available only for *subsequent* updates of that node. Verify radio speed, packet loss, power failure, and Relay hops with real hardware before wider rollout. No throughput guarantee is made.

Docs: https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32c3/api-reference/bluetooth/esp-ble-mesh.html and https://github.com/espressif/esp-now.
