# Mesh OTA через веб-шлюз — технический протокол v0.3.11-dev

Статус: **экспериментальная реализация в коде**; работоспособность на
реальном ESP32 подтвердить отдельно. Не Bluetooth Mesh SIG DFU/BLOB.

## Поток
1. Браузер читает строго APP onoff_server.bin; самостоятельно вычисляет
   SHA-256 (WebCrypto, если разрешён; fallback для обычного HTTP).
2. Авторизованная `POST /api/ota/node/start` получает
   `{address,chip:"C3"|"S3",size,sha256}`. Шлюз проверяет, что узел
   зарегистрирован, недавно отвечал и объявил `OTA1` с этим чипом.
3. Шлюз шлёт AppKey-защищённый Vendor START на конкретный Unicast.
   Узел проверяет chip, OTA partition и размер, вызывает esp_ota_begin.
4. Браузер посылает POST /api/ota/node/chunk (бинарные байты,
   X-OTA-Offset). Шлюз передаёт 96 байт DATA в Mesh, ждёт STATUS от
   правильного session/node, возвращает браузеру подтверждённый offset.
   Повтор того же блока после потери ACK не записывает данные заново.
5. FINISH: узел сравнивает полный SHA-256, вызывает esp_ota_end,
   читает esp_app_desc и требует project_name=onoff_server,
   активирует неактивный OTA APP через esp_ota_set_boot_partition,
   подтверждает и только затем перезагружается.
6. Неудача/отмена вызывает ABORT (если возможно), никакой
   переустановки Mesh/NVS и никакого изменения running APP.

## Vendor opcodes (CID 0x02E5, тестовый CID Espressif)
- 0x36 START [session:2, size:4, chip:1, SHA256:32]
- 0x37 DATA [session:2, offset:4, bytes:1..96]
- 0x38 FINISH [session:2]
- 0x39 ABORT [session:2]
- 0x3A STATUS [session:2, next_offset:4, status:1]
- 0x3B PEER_HELLO [sequence:2] — отдельное peer-to-peer сообщение
(для версии ранее используются 0x34 GET и 0x35 STATUS).

Передача выполняется **только вручную**, **одному узлу**, от
авторизованного шлюза (в HTTP API и Mesh AppKey), только при наличии
поддержки OTA1 у узла. Старый узел без OTA1 — сначала USB.
На портале запрещено выбирать gateway .bin вместо node .bin.

## Ограничения / дальнейшая работа
- Процесс требует открытой страницы браузера до завершения, может быть
  долгим на слабой Mesh-сети, timeout по блокам с повтором.
- Состояние передачи не сохраняется после перезапуска шлюза или браузера;
  после ошибки потребуется новая сессия. Старая APP не изменяется.
- Для производства: перейти на SIG Mesh DFU/BLOB (в ESP-IDF 5.5.x
  обозначен как preview), передавать чанки эффективнее, организовать
  resume и multicast с контрольными точками.
- SHA-256 и шифрование AppKey защищают от случайной порчи и внешней
  передачи без ключа, **но не заменяют цифровую подпись прошивки**.
- Нужны: CI для C3/S3, моделирование потери ACK, тест отключения питания
  в середине/конце, проверка OTA rollback, масштабирование до десятков
  узлов, тест дальнего Relay-тракта с выключенным шлюзом.
