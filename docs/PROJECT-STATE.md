# ESP32 AutoMesh — контекст проекта для следующего чата
Актуализировано: 2026-11-14. Рабочая ветка: **main**, дополнительных веток нет.
GitHub: https://github.com/DeadSoulf/esp32-mash (приватный репозиторий).

## Цель
ESP32-C3 SuperMini и Waveshare ESP32-S3-Zero (4 МБ Flash) образуют BLE Mesh.
Один ESP32 может быть **шлюзом** (Provisioner + Wi-Fi веб-панель), остальные —
**узлами** (Node + Relay). После первичной регистрации новые устройства
**обязательно подтверждаются администратором**. Автоматически регистрировать
чужие ESP32 запрещено. Пользователь предпочитает всё собирать в
**GitHub Actions** (ESP-IDF 5.5.3), а не компилировать на ноутбуке.

## Уже реализованные функции (по исходникам)
- USB Windows-установщик: выбор COM-порта, выбор роли, одно окончательное
  подтверждение. Предварительно проверяет тип чипа, Flash 4 МБ и SHA-256
  файлов, сохраняет полный дамп Flash в локальные Backups, сверяет тот же
  чип/MAC перед записью. По умолчанию NVS не очищается; специальный
  --erase-nvs нужен только для намеренной очистки.
- Первая настройка шлюза без сохранённого роутера: открытая Wi-Fi AP
  AutoMesh-XXXXXX; создание одного пароля администратора (от 6 символов);
  он хранится как PBKDF2-хеш в NVS. Сеть AP не защищена паролем до настройки
  домашней сети — использовать в контролируемом месте.
- Веб-панель: поиск Wi-Fi, настройка роутера, авторизация без бесконечных
  повторов HTTP 401/429, список Mesh-кандидатов, ручной допуск,
  переименование, поиск/мигание LED, проверка связи, отображение
  фактической версии/ELF ID шлюза и версии узла (узлы с поддержкой запроса).
- ESP32-C3 SuperMini: status LED GPIO8 active-low.
- Waveshare ESP32-S3-Zero: RGB WS2812 через RMT на GPIO21, индикация
  соединения/отсутствия связи/поиска.
- Веб-OTA шлюза: только APP .bin подходящего чипа, в неактивный раздел,
  проверка образа и необязательный SHA-256, перезагрузка/rollback;
  NVS и Mesh-ключи сохраняются.
- BLE Mesh: настройки и сетевые ключи в NVS, узлы Relay с маршрутизацией
  через соседей. Шлюз является Provisioner, но **не обязательным узлом
  пересылки** после регистрации.
- Версия 0.3.11-dev: добавлен peer-to-peer heartbeat между узлами с
  периодичностью ~60 секунд (AppKey + All Nodes, TTL 4). LED отмечает
  доступность другого участника Mesh, не только шлюза.
- Версия 0.3.11-dev: реализован экспериментальный выбор **одного OTA1 узла**
  и передача его APP .bin из браузера через шлюз по BLE Mesh. Данные
  передаются блоками по 96 байт, с подтверждениями, SHA-256 и проверкой
  чипа и project_name=onoff_server на узле до переключения раздела.
  Долгая передача по радио, без автоматического запуска OTA.
- Windows ZIP v0.3.11-dev: Web-OTA/{gateway-*.bin,Nodes/node-*.bin,
  SHA256SUMS.txt,README-RU.txt}. Все OTA образы создаёт GitHub Actions.
- Секция «Сменить ключ администратора» находится в самом низу страницы.

## Версия 0.3.12-dev: управление устройствами
- Технический UUID больше не отображается пользователю в таблице,
  OTA-списке или уведомлениях. Он остаётся в JSON/API и во внутренней
  базе для адресации правильного устройства.
- Зарегистрированное устройство можно удалить кнопкой «Удалить
  устройство». Подтверждение обязательно. Служебный API POST
  /api/remove принимает UUID и требует авторизации администратора.
- ESP-IDF удаляет запись SDK Provisioner асинхронно; только по
  завершении с успехом шлюз стирает запись из реестра, RAM-кеша и
  зеркала meshdb в NVS. При ошибке удаления строка остаётся.
- Физическая ESP32 **не сбрасывается дистанционно** и сохраняет
  Mesh NetKey/AppKey. Простое удаление из шлюза не отзывает
  криптографические права узла: для полного исключения устройства
  необходимо сбросить его локальную Mesh-конфигурацию и при
  необходимости заменить общесетевые ключи.
- Для новых неподключённых устройств остаётся кнопка «Отклонить».
- Документ для продолжения в новом чате: эта страница; применять
  изменения только в main и собирать в GitHub Actions.

## Что НЕ обещать как уже завершённое
1. **Сборка, работа на реальном железе и выпуск v0.3.11-dev должны быть
   подтверждены результатом GitHub Actions и испытанием**. Исходники и
   тесты сами по себе ещё не подтверждают стабильность.
2. Старые узлы без протокола OTA1 **не умеют принимать обновление по Mesh**.
   Их нужно единожды обновить через Windows USB-установщик.
3. BLE Mesh Relay работает без шлюза, но веб-панель/OTA/новые допуски
   недоступны, пока шлюз не вернётся. **Резервного Provisioner и
   автоматических выборов нового шлюза нет**. Смена Provisioner требует
   защищённой синхронизации Mesh-ключей и node DB.
4. Peer heartbeat — связь «сосед-сосед» и обнаружение присутствия;
   распределённая пользовательская автоматика и выбор маршрутов
   приложением ещё не реализованы (маршрутизация — штатный BLE Mesh Relay).
5. OTA протокол **экспериментальный**, не Bluetooth SIG Mesh DFU/BLOB.
   При высокой нагрузке сети или дальних узлах потребуется нагрузочное
   тестирование, паузы, возобновляемая передача и, возможно, переход на
   стандартный ESP-IDF Mesh DFU (preview). Массового OTA нет.
6. SHA-256 — контроль целостности, а не подпись производителя:
   необходимы проверка подписей и доверенные ключи для недоверенного
   окружения. BLE Mesh No-OOB commissioning подвержен активной подмене
   в радиозоне, применять только в контролируемых условиях.

## Файлы и роли
- `gateway/main/main.c` — Provisioner, Generic Client, Vendor model,
  версии и Mesh OTA relay;
- `gateway/main/automesh_web.c` — авторизованные HTTP API;
- `gateway/main/gateway_index.html` — веб-интерфейс;
- `gateway/main/automesh_gateway_node_ota.c` — передача OTA блоков и ACK;
- `gateway/main/automesh_bridge.c` — реестр узлов и проверка OTA1;
- `node/main/main.c` — Node, Relay, Vendor version, peer heartbeat;
- `node/main/automesh_node_ota.c` — приём/проверка OTA, rollback;
- `*/main/automesh_ota_protocol.h` — общие opcodes и бинарный протокол;
- `Windows-Installer/` — Python/EXE установщик, манифест, ZIP;
- `.github/workflows/esp-idf-c3.yml` — матрица C3/S3 × Gateway/Node,
  Python-тесты, загрузка бинарников, упаковка ZIP, GitHub Release.
- `docs/MESH-OTA-DESIGN.md` и `docs/MESH-RESILIENCE.md`.

## Безопасное продолжение
1. Проверить **последнюю сборку Actions**, открыть логи ошибок
   компиляции; исправлять через GitHub и повторять до зелёной матрицы.
2. Проверить содержимое ZIP: Web-OTA содержит 4 APP .bin и SHA256SUMS,
   не USB образы; --self-test Windows EXE.
3. На тестовой плате проверить: версия узла OTA1 по Mesh, один малый OTA,
   затем полный OTA; при обрыве питание/BT старая APP работает; NVS/ключи
   сохраняются и OTA-rollback корректен.
4. Проверить отключение шлюза: два узла остаются в Mesh, пересылают PEER_HELLO,
   сохраняют контакты и состояние; если единственный Relay падает,
   изолированный участок может потерять достижимость.
5. Сделать полномасштабные проверки с несколькими relay-узлами,
   маршрутизацией и нагрузкой OTA. Не стирать NVS при обновлении.
6. Учитывать, что в документации/исходниках могут оставаться прежние
   комментарии от версий 0.3.2–0.3.10: приоритет — актуальные функции
   и проверенные результаты CI/железа, не старые описания.

**Не сохранять реальные пароли, приватные Mesh-ключи, IP-адреса,
MAC-адреса, USB-дампы и личные данные в публичной документации.**

## v0.3.15-dev — Wi-Fi вниз страницы и Mesh OTA timeout

- В `gateway/main/gateway_index.html` раздел `id="wifiSetup"`
  находится непосредственно перед `id="adminChange"` в самом низу
  контента, после устройств, OTA и «Радиосвязь и индикация».
- Получена пользовательская ошибка `ESP_ERR_TIMEOUT` при попытке
  обновить узел через веб-интерфейс шлюза. Анализ исходников выявил
  вероятный блокирующий участок: `esp_ota_begin(part,size,...)` внутри
  BLE Mesh callback до ACK START. Непосредственное подтверждение
  аппаратной первопричины ещё требует UART-логов и теста на ESP32.
- В `node/main/automesh_node_ota.c` добавлены FreeRTOS очередь
  и задача `node_mesh_ota`: в Mesh callback только проверка,
  копирование пакета и постановка в очередь; Flash выполняется в
  worker. `esp_ota_begin(...,OTA_WITH_SEQUENTIAL_WRITES,...)`
  вместо предварительного массового стирания. START повторный
  при совпадающем session/image не отвергает отправителя.
- В `gateway/main/automesh_gateway_node_ota.c` START/DATA можно
  повторять до 3 раз с ожиданием STATUS; FINISH/ABORT не повторяются
  автоматически (после FINISH узел может уже перезагрузиться).
  В журнале: stage, node, offset, attempt и timeout.
- `gateway/main/main.c`: периодические Mesh-ping и запросы
  версии приостанавливаются, пока действует OTA.
- `gateway/main/automesh_web.c`: HTTP-ошибки содержат `stage`
  (start/data/finish/abort), интерфейс выводит этап сбоя.
- Критично: для OTA1-узлов прежних версий, у которых START не
  подтверждается, может потребоваться **одна USB-прошивка** исправленной
  версии при сохранении NVS и Mesh-ключей. Не стирать NVS автоматически.
- Новый регрессионный тест `tests/test_mesh_ota_timeout.py`.
  Нужно проверить GitHub Actions матрицу C3/S3 для шлюза и узла,
  ZIP `AutoMesh-v0.3.15-dev.zip`, затем физическое OTA сначала
  на одном узле, после — проверка сохранения Mesh-конфигурации,
  rollback и устойчивости сети при пропадании пакетов.
- Изменения только в `main`, без новых веток.


## v0.3.16-dev — карта прямых соседей BLE Mesh (2026-11-15)

- Реализована вкладка `Карта Mesh` (`gateway/main/gateway_index.html`)
  рядом со списком устройств. Реальные зарегистрированные узлы, шлюз,
  перетаскивание, увеличение/уменьшение, панорамирование, свежесть
  наблюдений и легенда уровня RSSI.
- **Это не фиксированная топология маршрутов.** Для определения
  непосредственных радиососедей вводится opcode
  `AUTOMESH_NEIGHBOR_BEACON` (0x3C) с TTL=1. Промежуточные
  Relay-узлы не могут переслать такой маяк. Принимающие ESP32
  используют `esp_ble_mesh_msg_ctx_t.recv_rssi`. Обычные
  многопрыжковые `PEER_HELLO` сохраняются, но не используются
  для построения линий.
- Узлы раз в 60–72 секунды направляют шлюзу компактный
  AppKey-защищённый отчёт `AUTOMESH_NEIGHBOR_REPORT` (0x3D):
  до 3 наиболее сильных прямых соседей, с RSSI. Шлюз тоже
  посылает TTL=1 маяк и измеряет принятые непосредственно.
- Шлюз хранит текущие наблюдения исключительно в RAM
  (`gateway/main/automesh_topology.c`), срок 210 секунд.
  `GET /api/mesh/topology` требует авторизации и фильтрует
  адреса через `automesh_mesh_address_approved`. Только
  зарегистрированные участники, без секретов/MAC/UUID в карте.
- Одна или обе стороны могут подтвердить прямую связь: пунктир /
  сплошная линия; RSSI отражает качество полученного маяка
  в `dBm`, а не дальность в метрах. Положение графа не сохраняется.
  HTML использует локальные SVG/JS без CDN и доступен офлайн.
- Карта опрашивает API примерно раз в 15 секунд только при
  открытой вкладке; сами измерения радио — около раз в минуту.
- Прошивки с предыдущими opcodes (без 0x3C/0x3D) всё ещё работают
  и сохраняют Mesh; на карте их связи не выдумываются.
- Документировать и проверить в CI: веб-JS `node --check`,
  Python regressions, четыре ESP-IDF сборки, Windows ZIP.
  **Аппаратный тест ещё нужен:** два-три узла, разнести по
  комнатам; проверить RSSI, односторонние/двусторонние связи,
  отсутствие фиктивных ребёр после отключения, обновление старого
  узла без очистки NVS, Mesh OTA при дополнительном трафике.
- Работать только в `main`. История сигналов не нужна.


## v0.3.17-dev — исправление неработающего Mesh OTA

Жалоба пользователя: **обновление узлов через веб-интерфейс шлюза
продолжает не работать**, несмотря на исправления тайм-аутов v0.3.15.
Проверка исходников ESP-IDF выявила существенную ошибку:

- Шлюз отправлял клиентскую vendor-команду с `need_rsp=false`
  и сам ожидал статус через semaphore, но callback обрабатывал
  `AUTOMESH_NODE_OTA_STATUS` только при
  `ESP_BLE_MESH_MODEL_OPERATION_EVT`. В клиентской реализации
  Espressif непарные ответы поступают через
  `ESP_BLE_MESH_CLIENT_MODEL_RECV_PUBLISH_MSG_EVT`
  (`param->client_recv_publish_msg`). Из-за этого даже полученный
  ответ мог быть проигнорирован и превращён в ESP_ERR_TIMEOUT.
- Исправлено в `gateway/main/main.c`: слушаются оба события;
  для OTA STATUS проверяется модель, контекст, длина 7 и
  вызывается `automesh_gateway_node_ota_on_status`. Сама OTA-сессия
  проверяет адрес узла, request ID, ожидаемое смещение и статус.
- В `node/main/automesh_node_ota.c`: раньше ответ использовал
  полученный ctx со значением `send_ttl` не заданным явно.
  Теперь `reply.send_ttl=5` для ретрансляции статуса через
  Mesh-узлы. Добавлена диагностика отправки ACK и его ошибок.
- Добавлен `tests/test_mesh_ota_ack_delivery.py` для предотвращения
  повторения этой ошибки. Версия обеих прошивок — v0.3.17-dev.
- Сначала обновить **шлюз** из `Web-OTA/gw-c3.bin` или
  `gw-s3.bin`, затем один соседний узел через панель. Старый узел
  может не уметь отвечать через Relay; для первого исправления тогда
  нужна **USB-прошивка без очистки NVS**.
- Не изменены правила допуска устройств, Mesh NetKey/AppKey, работа
  Wi-Fi шлюза, отдельный модуль карты и сохранение NVS. Работать
  только в `main`; документ обновлён для продолжения в новом чате.
- **Не выдавать успешную компиляцию за аппаратное подтверждение.**
  Нужны две ESP32, UART-логи обоих устройств, однократный START,
  затем полная передача, проверка SHA-256, перезагрузки и OTA rollback.

  `meshSvg` с `meshScene`; `settingsTab` — `wifiSetup`,
  `adminChange` и `settingsMessage`. Ссылки Wi-Fi/IP перенесены
  в `wifiSetup`.
- У карты нет заголовка, панелей состояния, кнопок и легенды.
  Оставлены перетаскивание, масштабирование колёсиком и сброс
  двойным щелчком. Диагностика состояния карты передаётся
  доступным средствам чтения экрана через `aria-label`.
- На первом запуске после задания ключа администратора открываются
  настройки Wi-Fi (`state.setup_mode`), но вкладка не переключается
  заново после каждого трёхсекундного обновления. Смена ключа
  не выталкивает пользователя из вкладки.
- Доступ к трём вкладкам только после успешных защищённых
  `/api/status` и `/api/devices`; при неверном ключе или выходе
  используется `hideMainTabs()`. Добавлен стиль
  `[hidden]{display:none!important}`, чтобы flex-стили не
  раскрывали скрытую навигацию.
- Для Wi-Fi и смены ключа используется прежний API. Результат
  действия отображается в `settingsMessage` непосредственно
  в настройках (а не в скрытой форме авторизации).
- Никаких изменений в настройках BLE Mesh, NVS, ключах, допуске
  устройств, радио-протоколе, OTA устройства. Сборка четырёх
  прошивок и ZIP через GitHub Actions. Добавлен
  `tests/test_tabs_settings_layout.py`, обновлены тесты карты.
- Все изменения только в `main`. Физическую работу панели
  необходимо проверить на тестовом шлюзе.
