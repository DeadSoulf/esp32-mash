# ESP32 AutoMesh — контекст проекта для следующего чата
Актуализировано: 2026-11-14. Рабочая ветка: **main**, дополнительных веток нет.
GitHub: https://github.com/DeadSoulf/esp32-mash (приватный репозиторий).

## Цель
ESP32-C3 SuperMini и Waveshare ESP32-S3-Zero (4 МБ Flash) образуют BLE Mesh.
Один ESP32 может быть **шлюзом** (Provisioner + Wi-Fi веб-панель), остальные —
**узлами** (Node + Relay). После первичной регистрации новые устройства
**обязательно подтверждаются администратором**. Автоматически регистрировать
чужие ESP32 запрещено. Пользователь предпочитает всё собирать в
**GitHub Actions** (ESP-IDF 5.5.3), а не компилировать на ноутбуке.

## Уже реализованные функции (по исходникам)
- USB Windows-установщик: выбор COM-порта, выбор роли, одно окончательное
  подтверждение. Предварительно проверяет тип чипа, Flash 4 МБ и SHA-256
  файлов, сохраняет полный дамп Flash в локальные Backups, сверяет тот же
  чип/MAC перед записью. По умолчанию NVS не очищается; специальный
  --erase-nvs нужен только для намеренной очистки.
- Первая настройка шлюза без сохранённого роутера: открытая Wi-Fi AP
  AutoMesh-XXXXXX; создание одного пароля администратора (от 6 символов);
  он хранится как PBKDF2-хеш в NVS. Сеть AP не защищена паролем до настройки
  домашней сети — использовать в контролируемом месте.
- Веб-панель: поиск Wi-Fi, настройка роутера, авторизация без бесконечных
  повторов HTTP 401/429, список Mesh-кандидатов, ручной допуск,
  переименование, поиск/мигание LED, проверка связи, отображение
  фактической версии/ELF ID шлюза и версии узла (узлы с поддержкой запроса).
- ESP32-C3 SuperMini: status LED GPIO8 active-low.
- Waveshare ESP32-S3-Zero: RGB WS2812 через RMT на GPIO21, индикация
  соединения/отсутствия связи/поиска.
- Веб-OTA шлюза: только APP .bin подходящего чипа, в неактивный раздел,
  проверка образа и необязательный SHA-256, перезагрузка/rollback;
  NVS и Mesh-ключи сохраняются.
- BLE Mesh: настройки и сетевые ключи в NVS, узлы Relay с маршрутизацией
  через соседей. Шлюз является Provisioner, но **не обязательным узлом
  пересылки** после регистрации.
- Версия 0.3.11-dev: добавлен peer-to-peer heartbeat между узлами с
  периодичностью ~60 секунд (AppKey + All Nodes, TTL 4). LED отмечает
  доступность другого участника Mesh, не только шлюза.
- Версия 0.3.11-dev: реализован экспериментальный выбор **одного OTA1 узла**
  и передача его APP .bin из браузера через шлюз по BLE Mesh. Данные
  передаются блоками по 96 байт, с подтверждениями, SHA-256 и проверкой
  чипа и project_name=onoff_server на узле до переключения раздела.
  Долгая передача по радио, без автоматического запуска OTA.
- Windows ZIP v0.3.11-dev: Web-OTA/{gateway-*.bin,Nodes/node-*.bin,
  SHA256SUMS.txt,README-RU.txt}. Все OTA образы создаёт GitHub Actions.
- Секция «Сменить ключ администратора» находится в самом низу страницы.

## Версия 0.3.12-dev: управление устройствами
- Технический UUID больше не отображается пользователю в таблице,
  OTA-списке или уведомлениях. Он остаётся в JSON/API и во внутренней
  базе для адресации правильного устройства.
- Зарегистрированное устройство можно удалить кнопкой «Удалить
  устройство». Подтверждение обязательно. Служебный API POST
  /api/remove принимает UUID и требует авторизации администратора.
- ESP-IDF удаляет запись SDK Provisioner асинхронно; только по
  завершении с успехом шлюз стирает запись из реестра, RAM-кеша и
  зеркала meshdb в NVS. При ошибке удаления строка остаётся.
- Физическая ESP32 **не сбрасывается дистанционно** и сохраняет
  Mesh NetKey/AppKey. Простое удаление из шлюза не отзывает
  криптографические права узла: для полного исключения устройства
  необходимо сбросить его локальную Mesh-конфигурацию и при
  необходимости заменить общесетевые ключи.
- Для новых неподключённых устройств остаётся кнопка «Отклонить».
- Документ для продолжения в новом чате: эта страница; применять
  изменения только в main и собирать в GitHub Actions.

## Что НЕ обещать как уже завершённое
1. **Сборка, работа на реальном железе и выпуск v0.3.11-dev должны быть
   подтверждены результатом GitHub Actions и испытанием**. Исходники и
   тесты сами по себе ещё не подтверждают стабильность.
2. Старые узлы без протокола OTA1 **не умеют принимать обновление по Mesh**.
   Их нужно единожды обновить через Windows USB-установщик.
3. BLE Mesh Relay работает без шлюза, но веб-панель/OTA/новые допуски
   недоступны, пока шлюз не вернётся. **Резервного Provisioner и
   автоматических выборов нового шлюза нет**. Смена Provisioner требует
   защищённой синхронизации Mesh-ключей и node DB.
4. Peer heartbeat — связь «сосед-сосед» и обнаружение присутствия;
   распределённая пользовательская автоматика и выбор маршрутов
   приложением ещё не реализованы (маршрутизация — штатный BLE Mesh Relay).
5. OTA протокол **экспериментальный**, не Bluetooth SIG Mesh DFU/BLOB.
   При высокой нагрузке сети или дальних узлах потребуется нагрузочное
   тестирование, паузы, возобновляемая передача и, возможно, переход на
   стандартный ESP-IDF Mesh DFU (preview). Массового OTA нет.
6. SHA-256 — контроль целостности, а не подпись производителя:
   необходимы проверка подписей и доверенные ключи для недоверенного
   окружения. BLE Mesh No-OOB commissioning подвержен активной подмене
   в радиозоне, применять только в контролируемых условиях.

## Файлы и роли
- `gateway/main/main.c` — Provisioner, Generic Client, Vendor model,
  версии и Mesh OTA relay;
- `gateway/main/automesh_web.c` — авторизованные HTTP API;
- `gateway/main/gateway_index.html` — веб-интерфейс;
- `gateway/main/automesh_gateway_node_ota.c` — передача OTA блоков и ACK;
- `gateway/main/automesh_bridge.c` — реестр узлов и проверка OTA1;
- `node/main/main.c` — Node, Relay, Vendor version, peer heartbeat;
- `node/main/automesh_node_ota.c` — приём/проверка OTA, rollback;
- `*/main/automesh_ota_protocol.h` — общие opcodes и бинарный протокол;
- `Windows-Installer/` — Python/EXE установщик, манифест, ZIP;
- `.github/workflows/esp-idf-c3.yml` — матрица C3/S3 × Gateway/Node,
  Python-тесты, загрузка бинарников, упаковка ZIP, GitHub Release.
- `docs/MESH-OTA-DESIGN.md` и `docs/MESH-RESILIENCE.md`.

## Безопасное продолжение
1. Проверить **последнюю сборку Actions**, открыть логи ошибок
   компиляции; исправлять через GitHub и повторять до зелёной матрицы.
2. Проверить содержимое ZIP: Web-OTA содержит 4 APP .bin и SHA256SUMS,
   не USB образы; --self-test Windows EXE.
3. На тестовой плате проверить: версия узла OTA1 по Mesh, один малый OTA,
   затем полный OTA; при обрыве питание/BT старая APP работает; NVS/ключи
   сохраняются и OTA-rollback корректен.
4. Проверить отключение шлюза: два узла остаются в Mesh, пересылают PEER_HELLO,
   сохраняют контакты и состояние; если единственный Relay падает,
   изолированный участок может потерять достижимость.
5. Сделать полномасштабные проверки с несколькими relay-узлами,
   маршрутизацией и нагрузкой OTA. Не стирать NVS при обновлении.
6. Учитывать, что в документации/исходниках могут оставаться прежние
   комментарии от версий 0.3.2–0.3.10: приоритет — актуальные функции
   и проверенные результаты CI/железа, не старые описания.

**Не сохранять реальные пароли, приватные Mesh-ключи, IP-адреса,
MAC-адреса, USB-дампы и личные данные в публичной документации.**
